# 발주자에게 기준 커밋을 전달하고, 최신 화면과 일치하는지 확인

main에 직접 작업하거나 force push하지 않습니다. 기존 업체 작업과 충돌이 있으면 덮어쓰지 말고 변경 범위를 협의합니다.

2. 개발 환경 구성 및 실행

2.1 기술 구성

7. 회사 선택 및 로고 규칙

  • 회사 목록: 동원약품, 신덕약품, 보덕메디팜, 아이팜코리아, 인천약품, 신덕팜. 공통 목록은 shared/company-branding.ts, 기본 색상·이미지는 App.tsx에 있습니다.
  • 홈은 특정 회사에 속하지 않는 공통 화면입니다. 홈 중앙에는 회사 로고·현재 주문중 문구를 표시하지 않고 ‘주문할 회사를 선택하세요’를 안내합니다.
  • 헤더 선택 버튼은 ‘주문회사 이동’입니다. 선택 목록에는 회사명만 표시합니다. 상단에 삭제된 회사 책갈피를 복원하지 마세요. 홈 회사 카드는 별도 기능입니다.
  • 홈 이외 화면의 회사 로고는 헤더 정중앙에 테두리·배경 박스 없이 배치합니다. 중앙 로고 클릭 편집은 유지합니다.
  • 홈 카드 로고: 업로드 standard → 기본 이미지 → 텍스트 표시. 헤더: 업로드 header → 기본 헤더 이미지 → 업로드 standard → 기본 이미지 → 회사명 표시.
  • 지원 종류: standard/header. 파일은 PNG·JPEG·WEBP, 실제 바이트 기준 512KiB 이하, 가로·세로 각각 1~4096px. SVG는 지원하지 않습니다.
  • 서버는 파일명만이 아니라 Base64·이미지 형식·크기를 검사합니다. 검증을 제거하거나 프런트엔드만의 검사로 대체하지 마세요.

8. 현재 API 계약

아래는 실제 등록된 업무 API입니다. 주문·결제·사용자 인증용 API가 이미 존재한다고 가정하지 마세요. 회사명 경로는 URL 인코딩합니다.

메서드·경로요청정상 응답
GET /api/favorites없음{ favoriteProductIds: string[] }
PUT /api/favorites/:productId본문 불필요저장 후 같은 응답
DELETE /api/favorites/:productId본문 불필요삭제 후 같은 응답
GET /api/company-logos없음{ logos: [{ company, variant, url, updatedAt }] }
GET /api/company-logos/:company/:variant/image없음이미지 바이트와 Content-Type. 로고 없음 404
PUT /api/company-logos/:company/:variant{ "dataUrl": "data:image/png;base64,..." }저장 후 { logos: [...] }
DELETE /api/company-logos/:company/:variant없음업로드 제거 후 { logos: [...] }. 화면은 기본 로고로 복귀

즐겨찾기 ID는 영문·숫자·밑줄·하이픈 1~64자입니다. 잘못된 회사/종류/입력은 400, 로고 용량 초과는 413, 서버 오류는 500과 { message } 형식으로 응답합니다. 이미지 요청 대상이 잘못된 경우도 400입니다. 새 API도 성공·실패를 구분하고 저장 실패를 성공처럼 표시하지 마세요.

orders주문번호·품목·수량·금액·상태·일자현재 실제 주문 처리 API 없음

운영 DB에 db:push 또는 post-merge.sh를 바로 실행하지 마세요.

post-merge.sh에는 db:push가 포함되어 있습니다. 자동 실행 경로에서도 스키마 삭제·형변환을 강제 승인하지 않습니다. 운영 반영은 백업 확인 → 변경 SQL 검토 → 개발/스테이징 검증 → 발주자 승인 → 반영 순서로 수행합니다. 이 절차는 권고이며 현재 버전 관리형 마이그레이션 체계가 완성되어 있다는 뜻은 아닙니다.

  • 실제 테이블·컬럼 기준은 shared/schema.ts입니다. SQL에서 컬럼명은 정의된 DB 이름을 사용합니다.
  • Neon 연결에서는 0행 결과 처리에 주의합니다. 현재 로고 저장소는 COALESCE/json_agg와 COUNT로 항상 결과 행을 받는 방식을 사용합니다.
  • 금액은 DB decimal과 프런트엔드 변환·반올림 정책을 정한 뒤 연동합니다. 화면 숫자만으로 결제 금액을 신뢰하지 마세요.
  • database/export/development-data.json은 과거 개발 DB 스냅샷이며 운영 백업·현재 DB 상태가 아닙니다. 앱 실행 시 자동 복원되지 않습니다.
  • 회사/약국별 주문과 잔고를 분리하려면 현재 스키마의 소유권 모델을 재검토해야 합니다. 임의 컬럼 추가보다 데이터 범위와 권한을 먼저 합의하세요.

10. 운영 적용 전 보안 필수 항목

  1. 실인증·권한: 서버에서 로그인 사용자와 회사/약국 접근 범위를 검증합니다. 브라우저가 보내는 userId/company만 신뢰하지 않습니다.
  2. 관리자 전용 변경: 회사 로고 수정·삭제 API에 인증과 관리자 권한을 적용합니다. 현재는 제한되어 있지 않습니다.
  3. 결제: 현재 결제 화면에 카드 정보 입력 UI가 있어도 실정보를 입력하지 않습니다. 실제 연동은 결제사업자의 안전한 호스팅/토큰화 방식을 설계하고, 카드번호·비밀번호 등을 DB·Git·로그에 저장하지 않습니다.
  4. 비밀값: 개발·운영 DB와 인증정보를 분리합니다. 저장소, PR 설명, 화면 캡처, 메신저에 비밀값을 첨부하지 않습니다.
  5. 로그: 현재 API 응답을 일부 기록하는 로직이 있습니다. 개인정보·주문·결제 API를 추가하기 전 로그 마스킹과 기록 범위를 검토합니다.
  6. 약품 정보: 제품별 확인된 임상 정보만 표시합니다. 다른 약품 문구를 공통 기본값으로 채우지 않습니다.
  7. 인터넷 공개: 인증 없는 데모 API를 운영 준비 완료로 판단하지 않습니다. 테스트는 격리된 환경·비식별 데이터로 수행합니다.

11. 실제 업무 기능으로 적용하는 순서

아래는 추가 개발 권고입니다. 이번 매뉴얼 작성으로 구현되거나 승인된 작업이 아닙니다.

단계작업완료 판정
1. UI 적용최신 홈 디자인과 반응형을 확정. 기존 시스템이 다른 기술이면 HTML/CSS 구조를 참고하여 해당 시스템 방식으로 구현캡처 비교, 데이터·동작 유지, 범위 외 화면 무변경
2. 인증·소유권로그인, 회사/약국 범위, 로고 관리자, 개인 즐겨찾기 구현다른 사용자·회사 데이터에 접근할 수 없음
3. 조회 연동공지·품목·잔고·주문조회 API 계약 후 mock 배열 교체빈 결과/오류/로딩 구분, 금액과 기간 대조
4. 주문·반품가격·재고·수량 서버 검증, 중복 제출 방지, 트랜잭션 및 상태 이력실제 저장 후 재조회 일치, 실패 시 중복/부분 저장 없음
5. 결제·운영승인된 결제 연동, 결과 검증, 운영 반영 계획성공/실패/취소/재시도·중복 통보 처리 검증

React 컴포넌트를 JSP·PHP·서버 템플릿 등에 그대로 붙여 넣으면 실행되지 않습니다. 적용 대상 시스템의 기술 스택을 확인하고, UI 참고 적용과 React 전체 도입을 구분해 견적·일정을 합의하세요.

12. 개발·납품·반영 절차

  1. 발주자와 작업 범위·제외 범위·기준 커밋·대상 환경·완료 기준을 확정합니다.
  2. 전용 브랜치와 분리된 개발 DB로 작업합니다. 기존 UI/로직 변경은 최소화합니다.
  3. 타입 검사·빌드·변경 흐름 검증 후 PR을 제출합니다. 기존 경고와 신규 오류를 구분합니다.
  4. 발주자 검토 후 병합합니다. GitHub main 병합과 운영 반영은 별도 절차입니다.
  5. 운영 반영은 별도 승인을 받고, 데이터 변경이 있으면 이전 버전 호환성과 복구 방법까지 검토합니다.

납품물 체크리스트

  • PR 링크, 기준 커밋, 최종 커밋, 변경 파일 목록
  • PC·태블릿·모바일 전후 캡처 및 실제 작동 영상(상호작용 변경 시)
  • 실행 버전, 설치/빌드 명령, 검사 결과, 알려진 제약
  • 새 환경변수의 이름과 용도만, API 요청/응답 변경 내역
  • DB 변경 SQL·백업·적용·되돌림 계획(변경이 있을 때만)
  • 미구현 항목을 명시한 인수인계서. 단순 화면 표시를 기능 완료로 보고하지 않음
# 기본 검사
npm run check
npm run build

# 기존 로고 입력 검증 테스트
node --import tsx --test server/company-logo-input.test.ts

# 읽기 전용 API 응답 확인(개발 서버 실행 상태)
curl -i http://localhost:5000/api/company-logos
curl -i http://localhost:5000/api/favorites

위 명령은 검수 절차 안내입니다. 본 문서 작성 중 새로 실행했다는 의미는 아닙니다. 저장·삭제 테스트는 분리된 개발 환경에서만 수행합니다.

14. 외주 개발자에게 보낼 의뢰문

WOS 소스를 참고하여 합의한 화면/기능 개선을 요청드립니다. 먼저 기준 커밋과 첨부된 최신 화면이 일치하는지 확인해 주세요. 기존 시스템에 적용할 경우 기술 스택 차이를 확인한 뒤 적용 가능 범위와 추가 개발 범위를 구분해 주세요.

현재 소스에는 임시 데이터와 미완성 기능이 포함되어 있습니다. 화면이 있다는 이유로 주문·결제·로그인 연동이 완료되었다고 간주하지 말아 주세요. 디자인 작업에서는 기존 데이터·회사 선택·로고 처리 동작을 유지하고 합의하지 않은 API/DB/권한 변경은 하지 않습니다.

별도 작업 브랜치에서 개발한 뒤 PR로 제출해 주세요. 변경 파일, 실행 방법, 검사 결과, PC·모바일 캡처와 남은 제약을 포함해 주세요. main 병합·운영 반영·DB 변경은 각각 발주자 검토와 승인을 거칩니다. 저장소를 공개하거나 운영 비밀값을 문서/Git/로그에 포함하지 마세요.

이 문서는 현재 작업공간 소스를 확인하여 작성한 인수인계 자료입니다. GitHub 원격·운영 DB·운영 환경의 최신 상태 전체를 재검증한 감사 보고서는 아닙니다. 소스가 변경되면 기준 커밋과 API·구현 상태를 함께 갱신하세요. 브라우저 인쇄 기능으로 PDF 저장이 가능합니다.
